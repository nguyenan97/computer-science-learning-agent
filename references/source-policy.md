# Source policy

Select scope from goals, prerequisites and the [topic map](topic-map.md). Academic sources support theoretical or learning claims; official documentation/standards establish specified technical behavior; pinned implementation/tests demonstrate one implementation; instructor synthesis proposes connections. Label these roles. A topic map is project design, not evidence of proficiency or an external educational requirement.

## Research each lesson

Start with one measurable objective and 2–4 answerable research questions. Separate stable foundational claims from changing implementation details. Prefer original research, systematic reviews/meta-analyses and academic syntheses for pedagogy; official documentation, standards and official code/tests for technical claims. Age alone does not decide quality.

Use the smallest useful source set, often 3–6 (a heuristic). Record title/authors, URL, role, claim/section used, checked date, applicable version/commit, status (`read`, `metadata_only`, `unavailable`) and **inspection scope**: abstract, selected full-text sections, full text or only metadata. A downloaded PDF is not proof it was read; an abstract is not a methods review. Preserve original attribution when reorganizing material. Do not copy substantial source text into lessons.

For academic findings inspect population, task, comparison, delay, outcome and limits at the level actually accessible. Separate a paper's finding from the tutor's inference for programming education. Do not invent effect sizes, causal conclusions, recommendations or an exhaustive review. Flag corrections/retractions when discovered; if not examined, withhold affected numerical claims. Describe conflicts and what could discriminate between them.

The [learning-science review](../research/learning-science-review.md) and [access log](../research/deep-study-source-checks.json) provide initial checked evidence. They do not establish this agent's effectiveness, a universal schedule or optimal practice percentage.

## Read to answer and test a question

Explain the essential source-backed ideas, examples and code on the lesson page in
original words. Do not send the learner to a paper/repository/download to obtain the
main explanation or worked answer. Supplementary reading names a target section,
question and output: claim ledger, prediction, annotated trace, comparison or
experiment. Limit open browsing; collect unanswered questions for later. Distinguish
observed results, predicted results, inference and unverified claims.

Keep checked dates/statuses, hashes, access logs, repository-evaluation dossiers and
agent verification records in private artifacts or maintainer documentation. The
reader page uses concise relevant citations and a curated related-reading footer,
with descriptions of what each source adds. Preserve attribution. Include an access
or verification limitation on-page only when needed to interpret or run the lesson;
do not paste an internal audit table or repeated disclaimers into every lesson.

Check volatile facts at lesson time: API/dependency versions, support status, cloud limits, security advice and repository activity. Pin lab reproducibility versions separately; an old reproducible example is not automatically the latest production recommendation. On access failure, record the actual limit and use verified stable material, a local equivalent or defer. Keep uncertainty visible in both languages.

## Implementation/repository protocol

1. Derive a narrow search from the objective. Compare an official/specialist implementation with a popular relevant alternative when useful. GitHub is optional when a standard, local implementation or paper trace teaches the objective better.
2. Record maintainer, license, archive status, release/default-branch evidence and stars with a checked timestamp if obtainable. Missing/ambiguous fields are null with a reason. Popularity is discovery metadata, never a learning-quality or adoption guarantee.
3. Evaluate objective fit, authority, maintenance, code/tests, docs, setup cost and complexity. Select a manageable slice, usually one repository; explain the rejected alternative without invented composite scores.
4. Pin an immutable commit SHA (or release with resolved SHA); link precise file/function/test/benchmark targets. Assign a prediction, trace, defect repair or controlled comparison connecting behavior to the mental model.
5. Log working directory, runtime/dependency/data versions, seed, commands, expected observations and what the agent actually ran. Distinguish upstream execution, a local equivalent and code reading. Report benchmark workload/environment; one machine does not establish universal speed advantages.
6. Preserve license notices and attribution for redistributed code; check dependencies separately. Keep identifying submissions and source artifacts private.

No README-only link dump, unchecked generated API claims, stars-as-quality ranking or fake benchmarks. Offline access remains supported. Failed source checks and unrun labs remain explicit limits in the research record, with learner-relevant consequences explained where needed.
